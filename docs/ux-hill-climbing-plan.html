Research and proposal · 6 November 2026 · Untangle revision fe0eff1

Make Untangle easier to use, with agents doing the QA

Use Loom, Screen Studio, and Cap as the comparison set. Build a bounded loop that changes the real Qt app, runs tasks, inspects screenshots, and keeps only verified improvements.

You should receive a tested pull request and a short decision report. You should not have to click through each change yourself. This document proposes the system. The loop is not installed or running.

Historical proposal, 6 November 2026. Capability inventories and environment observations below describe that research snapshot. The pilot tools and scoped agent-review policy were later implemented; see the delivered evidence and current UI standards. This proposal is not a running service, current backlog, or standing release authorization.

The three comparison apps

These are the best fit for Untangle's job: make a recording, review it, and share it with little effort. This is a recommendation based on official documentation. We did not measure competitor task times or test their installed apps.

1 · The sharing standard

Loom

Compare setup choices, recording status, the finished take, and the path to a useful link. Its current Mac guide shows target and input choices, microphone feedback, a finished preview, and local Preview and Copy Link actions. Official walkthrough.

Untangle target: the user can tell what was saved, review that exact file, and distinguish a local path from a share link and its audience.

Loom's desktop app is Mac/Windows, not native Linux. Use it as a workflow reference. Features vary by platform and plan. Platform limits.

2 · The presentation standard

Screen Studio

Compare readable framing, cursor emphasis, zoom controls, and easy finishing. Its official guide describes automatic click-based zooms and editable zoom regions. Product · Zoom guide.

Untangle target: a clear preview and predictable framing, with fewer adjustments needed to produce a useful video. Later, assess automatic zoom and simple presentation presets.

Mac only. Use screen.studio as the source. The similarly named screenstudio.dev is a different site. Untangle's current composed video cannot provide every post-record edit without capture changes.

3 · The closest product reference

Cap

Compare local recording, editing, export, and optional sharing. Cap separates Instant uploads from local Studio projects. This is a useful reference for making the save destination clear. Official workflow.

Untangle target: local recording works on its own. Sharing is a clear, separate choice. Export and upload failures preserve the original.

Cap advertises Linux support. Its installation guide lists an x86_64 Debian package, while some pages differ on platform/package coverage. Verify the exact build before any Linux comparison. Installation. Open source does not mean every commercial or cloud use is free. License.

OBS remains an engineering reference for source and audio control. It is too complex to be the main ease-of-use target. Tella and Supercut are useful editor references, but overlap with this set. Three stable references are enough to start.

Compare the same task and state, not whole products with one score. Collect dated official screenshots or demo frames for setup, recording, completion, review, and sharing. Record platform, version if known, source, and plan limits. If a matching state is unavailable, mark it missing. Do not invent it.

What to take from Theo

The likely video is Agents Sucked At UI (Until Today), indexed as 3 November 2026. I read a third-party transcript. Direct YouTube captions were unavailable, so this is not a claim of first-hand viewing.

The transcript describes screenshot reviews by several models, repeated changes, competitor references, and using one judge first to reduce cost. It also reports that scores changed with context and target scores. Keep the external references and iteration. Do not make “get 10/10” the completion rule.

A model can prefer a screenshot while the app becomes harder to use. Test task completion separately. Treat model ratings as advice, and retain the best verified version when an experiment fails.

The complete improvement loop

  1. Freeze the baselineSave revision, tasks, reference images, environment, and current results.
  2. Choose one problemState the user's task, the observed difficulty, and the expected improvement.
  3. Make one candidateChange one coherent area. Keep the last accepted version available.
  4. Run safe QAExercise production widgets, failure cases, screenshots, and the full required suite.
  5. Judge A against BFresh reviewers compare anonymous versions, task evidence, and fixed references.
  6. Keep or rejectKeep only a qualifying improvement. Record the result and repeat within budget.
  7. Deliver a pull requestAttach before/after evidence, test results, remaining limits, and rollback steps.
  8. Release after approvalPush/version first. Merge and install only under explicit release authority.

One controller owns the run. One builder changes code. A separate tester runs the scenarios. Fresh reviewers inspect evidence without seeing the builder's claims or target rating. Only one builder writes a candidate at a time.

On failure, reject the candidate and continue from the accepted revision. If main changes, update the branch and repeat affected verification before delivery. A crash, incomplete artifact set, or judge failure is an incomplete round, not a pass.

How a candidate earns acceptance

These are proposed operating rules. Calibrate them in the pilot. A score cannot cancel a failure.

  1. Pass the hard checks. Required tests and shell syntax pass. No new clipping, overlap, hidden main actions, lost focus, unsafe call, changed sharing default, or cleanup failure. A missing required test blocks acceptance.
  2. Show a task benefit. Record success, interactions, wrong turns, and time spent waiting. A visual-only change must improve legibility or hierarchy without making any task worse. Synthetic timing is a regression measure, not a human speed claim.
  3. Win a fresh comparison. Two reviewers prefer the candidate for the stated task and cite visible evidence. Randomize A/B order. Do not tell judges which is new or what score to reach. Disagreement means hold, revise, or reject.
  4. Pass reserved cases. Evaluate additional names, failures, and sizes that the builder did not use to tune the change. Keep test definitions outside the builder's allowed changes. A newly exposed case becomes a regression check in the next run.

Ask judges to rate hierarchy, readable text, control clarity, state feedback, consistency, and task effort separately on a 1–5 scale with examples for each level. Show the scores for diagnosis. Select candidates by the rules above, not an average alone.

Repeated model votes are not independent user research. Even separate Codex models share biases. A successful run establishes automated evidence of improvement, not proof that every user will prefer it.

Task evidence

The proposed catalog covered preparation, microphone recovery, pause/resume/stop, exact-file review, trim/export, sharing/archive failure, and quitting during work. Each task needed an initial state, synthetic inputs, allowed actions, completion/failure signals, and evidence. The baseline matrix was both themes, Camera/Screen, and 960x760/1120x840, with long names, empty/populated libraries, failures, keyboard use, and supported scale factors.

Scripted regression and discovery answer different questions. A fresh exploratory agent should receive the task and visible controls without the scripted solution; verify its wrong turns before treating them as defects. Current assertions and fixtures belong in the source, not a second catalog in this plan.

Original delivery decisions

The proposed order was a reproducible environment/current baseline, a comparison pack and machine-readable tasks, one bounded pilot PR, then expansion by measured need. The first pilot was exact saved-take review followed by return to setup. Before optimization, the environment should detect deliberately clipped text and a broken action. A separate policy decision was required before agent reviews could replace routine human visual QA.

Tests and comparator references were to stay read-only to the builder; any necessary changes needed separate review before resetting the baseline. The evidence record needed baseline/candidate commits, task version, image hashes, Qt/fonts/scale, mocks, action trace, assertions, durations, judge/prompt, and decision. Rejected rounds were to remain local.

UI-only permission excluded engine/audio/credentials/retention/format changes. A file allowlist alone could not protect mixed UI/business logic. Recurring runs were a future proposal after a successful pilot, with a single-run lock and resumable state, not a schedule created by this document. Region capture, automatic zoom, captions, and separate tracks each required their own design.

Models, cost, and stop rules

Use Codex (elhaam) first, as requested. The research used three Luna agents at low reasoning and the default service tier. No usage-limit failure occurred.

  • Luna at low reasoning handles reference updates, scenario summaries, and initial issue sorting.
  • Sol at low reasoning builds small UI candidates and performs the first visual review. Use a fresh instance for review.
  • A second Sol reviewer checks finalists and behavior risks. Escalate difficult design or ownership decisions to medium reasoning within Codex (elhaam).
  • When Elhaam usage runs out, save state and stop new calls. Report the limit. Switching accounts or providers is a separate decision.

After the environment and task bridge work, cap each optimization run at six candidate rounds, two hours of wall time, and no more than two finalist reviewers per candidate. Setup and implementation are separate work, not included in this run budget. Stop earlier after two rounds with no accepted gain, repeated judge disagreement, an environment failure, or a usage limit. Retain the best accepted candidate.

Log usage and elapsed time per round. This plan does not estimate a dollar cost from subscription usage. Set a token or spend cap if reliable usage data is available. Do not burn remaining quota just because it exists.

What “end to end” can mean here

Routine UX QA can be agent-owned. Agents can build, click, inspect actual Qt screenshots, test failures, review code, and prepare PR evidence. You make product and release decisions, without repeating the test script yourself.

Real microphone intelligibility, Bluetooth restoration, live Wayland behavior, sustained encoding and real service permissions need a separate acceptance lane. Build a dedicated test machine with synthetic media and isolated test accounts, then authorize the exact device/service checks. An agent can operate that machine. Your everyday desktop should not be the test lab. Until then, report these areas as unverified.

One policy decision is required before removing human visual QA. docs/ui-standards.md currently calls for human visual review. Deliverable 1 must include an approved policy change for copy, spacing, styling and UI navigation within the stated task. Replace manual visual QA in that scope with two fresh agent reviews, complete Qt screenshots, task traces and all required checks. Capture/audio behavior, authentication, uploads, deletion, retention and format changes stay outside that policy. It must not quietly label model review as human review.

Under the current repository rules, autonomous work ends at a reviewable PR. Merge, installation and runtime updates remain separate authorized actions. Before deployment, the change must be versioned and pushed. No screen readers, speech settings, real device checks, account sign-in or uploads are part of this research or the proposed ordinary loop.

Recommended next step: accept the three-app set, then implement deliverables 1–3 as the pilot. Require one complete successful run before adding a recurring schedule. No need to choose a large feature backlog first.
